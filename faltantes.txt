FALTANTES — Cambios hechos en el backend y pendientes para el frontend
App de viajes compartidos (back_blabla + blablacar)

PARTE 1 — CAMBIOS REALIZADOS EN EL BACKEND
================================================================================

Verificación: 46 tests pasan contra un PostGIS real. La imagen Docker se
construye, corre como usuario no-root y queda "healthy". La migración se probó
sobre el esquema viejo con datos inconsistentes.

1.1 Seguridad: IDOR (MEJORA_VANNA 1.1)
--------------------------------------------------------------------------------
- Todos los endpoints toman la identidad del JWT (claim `sub`).
- Las rutas NO cambiaron. Si el ID de la URL no es el del token → 403.
    PUT   /profile/{user_id}
    POST  /users/{user_id}
    PATCH /usuarios/{usuario_id}/foto
    POST  /trips/{driver_id}
    GET   /trips/active/{driver_id}
    GET   /mis-viajes/aprobados/{passenger_id}
    PATCH /trips/{trip_id}/pasajeros/{passenger_id}/cancelar
- La propiedad de viajes y solicitudes se verifica en la BD:
    GET   /trips/{trip_id}/requests      → solo el conductor del viaje
    PATCH /trips/{trip_id}/cancelar      → solo el conductor del viaje
    PUT   /requests/{request_id}/status  → solo el conductor del viaje
- POST /trips/{trip_id}/requests: el pasajero siempre es el usuario del token.
  El backend ignora passenger_id, sender_id, passenger_name, passenger_photo y
  passenger_rating del body. El nombre para la notificación se lee de la BD.
- GET /profile/{user_id} sigue abierto a cualquier usuario autenticado (perfil
  público: nombre, bio, preferencias, vehículos, foto).

1.2 Sobreventa de asientos (MEJORA_VANNA 1.2)
--------------------------------------------------------------------------------
- `trips.seats_available` ahora significa "asientos que QUEDAN".
- Aceptar una solicitud descuenta asientos dentro de una transacción con
  SELECT ... FOR UPDATE. Si ya no alcanzan → 409 y la solicitud sigue pendiente.
- Cuando un pasajero cancela, sus asientos se devuelven.
- Un índice único impide solicitudes vigentes duplicadas (mismo pasajero y viaje).
- Solo se pueden responder solicitudes en estado 'pendiente'.

1.3 Expiración de viajes (MEJORA_VANNA 1.3)
--------------------------------------------------------------------------------
- `departure_time` se interpreta como hora de America/Mexico_City (APP_TIMEZONE).
- Un viaje deja de aparecer en búsquedas a su hora de salida.
- Sigue "activo" para el conductor 2 horas después de la salida
  (TRIP_ACTIVE_GRACE_MINUTES=120). Después un job lo pasa a 'completado'.
- El conductor ya no queda bloqueado para siempre sin poder publicar.
- No se puede publicar un viaje con hora de salida en el pasado (400).
- No se puede solicitar un viaje que ya salió (400).

1.4 Docker (MEJORA_VANNA 1.5)
--------------------------------------------------------------------------------
- Dockerfile multi-stage con Python 3.12, usuario no-root, HEALTHCHECK y CMD
  propio (uvicorn, 2 workers). Sin build-essential, libpq-dev ni gdal.
- Nuevo backend/.dockerignore: solo entran app/ y requirements.txt.
- docker-compose.yml: sin Redis, sin `command`, y con variables nuevas
  (COGNITO_APP_CLIENT_ID, APP_TIMEZONE, TRIP_ACTIVE_GRACE_MINUTES, LOG_FORMAT).

1.5 Moderados y menores del backend
--------------------------------------------------------------------------------
- [M-01] El cliente JWKS es un singleton (antes se recreaba en cada request).
- [M-02] Se valida token_use == "access" y client_id (si se define
  COGNITO_APP_CLIENT_ID).

  igual sin push y deja un error claro en el log.
- [M-08] El health check `/` ya no expone versiones ni mensajes de error.
  Responde 503 si la BD está caída.
- [M-09] La búsqueda verifica el sentido de la ruta (ST_LineLocatePoint). El
  radio es configurable (SEARCH_RADIUS_M=500). El conductor no ve su propio
  viaje en la búsqueda.
- [M-10] Constraints CHECK (precio >= 0, asientos >= 0, seats_requested > 0),
  índice único parcial, triggers de updated_at y de sincronización de
  lat/lng con las geometrías.
- [M-11] RequestStatusUpdate.status solo acepta "aceptado" o "rechazado" (422).
- [M-12] Validación de rangos de lat/lng, precio, asientos (1 a 8) y longitud
  de textos. La foto debe ser una URL https (máximo 1024 caracteres).
- [M-13] Tests nuevos: IDOR, asientos y concurrencia, expiración, búsqueda,
  perfiles, JWT y health (46 en total).
- [M-14/M-15/M-16] Un solo helper `notify_users`. Envío multicast
  (send_each_for_multicast). Los tokens FCM dados de baja se borran solos.

  teléfono).
- [M-18 parcial] `distance_text` la calcula el servidor desde la ruta. Antes
  siempre quedaba NULL.
- Logging con request-id (header X-Request-ID) y formato JSON opcional.
- Se eliminó código muerto: imports sin usar, wrappers de database.py,
  get_active_trip_by_driver, fixtures con pytest-mock, el '5.0' fabricado de
  passenger_rating y el nombre "Usuario Cognito" hardcodeado.
- agentes.md actualizado con las reglas de autorización, asientos y fechas.

PARTE 3 — LO QUE FALTA EN EL FRONTEND (blablacar/blablacar)
================================================================================

La app actual SIGUE FUNCIONANDO con el backend nuevo: las rutas no cambiaron y
los campos que sobran se ignoran. Estos son los pendientes, en orden de
prioridad.

3.1 CRÍTICO
--------------------------------------------------------------------------------
[ ] F-01 (1.4) Descomentar Firebase.initializeApp() en lib/main.dart:14-16,
         antes de cualquier uso de Firebase. Sin esto no funcionan las push,
         el chat (Firestore) ni la subida de fotos (Storage).

[ ] F-02 (1.1) lib/services/api_service.dart — dejar de mandar campos que el
         backend ya ignora:
         - solicitarUnirse: quitar passenger_id, sender_id, passenger_name,
           passenger_photo y passenger_rating. Solo enviar
           {"seats_requested": n}.
         - publicarViaje: quitar distance_text (ahora lo calcula el servidor).
         Los IDs que van en la URL (userId, driverId, passengerId) SIGUEN siendo
         necesarios, pero deben salir SIEMPRE de currentUserIdProvider. Si no
         coinciden con el usuario del token, el backend responde 403.

[ ] F-03 Manejar los nuevos códigos de respuesta. El mensaje para el usuario
         viene en el campo "detail" del JSON:
         - 403 → "No tienes permiso..." (no debería pasar en el uso normal).
         - 409 al aceptar una solicitud → "No quedan asientos suficientes".
         - 409 al responder → "Esta solicitud ya fue respondida o cancelada".
         - 409 al cancelar un viaje → "El viaje ya no está activo" (antes 404).
         - 409 al publicar → "Ya tienes un viaje activo...".
         - 400 al publicar → "La hora de salida debe ser en el futuro".
         - 400 al solicitar → viaje propio, sin asientos o viaje que ya salió.
         - 422 → datos inválidos (asientos fuera de 1 a 8, precio negativo,
           textos muy largos, foto que no es https, estado que no es
           "aceptado"/"rechazado").
         Hoy muchos métodos devuelven solo true/false y se pierde el motivo.
